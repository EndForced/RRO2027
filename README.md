# FE2027 — генератор расстановок «Ремонт труб» (РРО 2026, Будущие инженеры)

```
go run ./main          # спросит количество и допишет расстановки в data/pats.bin
go test ./fastgen      # проверка 3000 полей на соответствие регламенту
```

## Алгоритм (`fastgen`)

1. **Подставки.** Случайно выбирается одна из 24 троек соседних перекрёстков у границы.
   Тройка и два ряда перед ней (6 перекрёстков) резервируются до расстановки паттернов.
2. **Паттерны.** Все 11 паттернов (10 пандусов, 20 секций, рис. 5) ставятся в случайном
   порядке, в случайные места и в одном из 4 направлений. Это перебор с возвратом по заранее
   посчитанным установкам; пересечение проверяется битовой маской `uint64`.
3. **Робот.** Случайный перекрёсток (нижний или верхний ярус) в той связной области, из которой
   можно доехать до подставок.
4. **Трубы.** Две ставятся на перекрёстки нижнего яруса, одна — на секцию верхнего. Нельзя ставить
   трубы на свободные ряды перед подставками и на перекрёсток вплотную к концу пандуса.
5. **Проверка решаемости.** Один BFS от робота, где трубы и подставки — препятствия.
   К каждой трубе должен быть подъезд, к каждой подставке — проезд.
6. **Эталонный маршрут.** Дейкстра запускается из ≤16 точек (старт, подъезды к трубам, перекрёстки
   перед подставками). Потом перебираются 6 порядков труб × 2 назначения подставок, подъезд к каждой
   трубе выбирается отдельно. Минимизируется сумма секций после первого касания трубы, трубы возятся
   по одной, пандус = 3 секции (п.3.2, п.8.3). Каждая труба кладётся поперёк направления подъезда.

Если какой-то шаг не удался, поле строится заново. Получается та же схема, что и в жеребьёвке:
сначала случайная расстановка, потом проверка решаемости.

## Правила регламента, которые проверяются

| Правило | Пункт |
|---|---|
| 10 пандусов и 20 секций, набор паттернов с рис. 5, 4 направления | 2.4, 6 |
| 2 трубы на нижнем ярусе, 1 на секции верхнего | 2.2, 6 |
| 2 красные + 1 синяя или 2 синие + 1 красная | 2.2 |
| Свободный проезд от старта до любой трубы | 2.2 |
| Между съездом пандуса и трубой есть перекрёсток | 2.2 |
| Подъезд к трубе с поперечной стороны | 6 |
| 3 подставки в ряд на соседних линиях у границы поля | 2.3 |
| Перед подставками свободны два ряда (6 перекрёстков) | 2.3 |
| Проезд от старта к перекрёстку перед подставками | 2.3 |
| Маршрут помещается в формат файла (≤112 клеток) | — |

Тест `fastgen/generator_test.go` проверяет все пункты таблицы на готовых полях независимо от
генератора. Каждый шаг маршрута он сверяет с графом из `matrixfactory`.

## Допущения

- Правило «перекрёсток между съездом пандуса и трубой» применяется к обоим концам пандуса.
- Эталонный маршрут кладёт трубу другого цвета на среднюю подставку (`Config.RespectColors`).
- Порядок сегментов маршрута: робот→труба→подставка→труба→… (по одной трубе, как в п.9).
- `MinLowerTubeDist = 6` между трубами нижнего яруса взят из старого генератора, в регламенте его нет.

## Старый генератор

Пакеты `generatorHandler`, `matrixgenerator` и `patsolve` оставлены для сравнения.
Он тратил ~0.6 с на поле. В 91% полей перед подставками были заняты перекрёстки, в 62% труба
стояла вплотную к пандусу. Новый тратит ~0.1 мс на поле в одном потоке, а `main` запускает

## Симулятор (`simulator`, `python/rrosim`)

```
go run ./simulator/cmd          # окно: http://127.0.0.1:8080
pip install -e python           # или просто добавить python/ в sys.path
python python/examples/explore.py
```

Сервер на Go использует ту же модель проездов, что и генератор (`matrixfactory` → `fastgen.Connects`).
Поле берётся случайно из `data/pats.bin`, если файл пуст — генерируется `fastgen`.
Окно — страница в браузере, Python-клиент общается с сервером по HTTP, зависимостей нет.

```python
from rrosim import Sim, IllegalCommand

sim = Sim()
sim.configure(sensor_cells=[(1, 0), (2, 0), (1, -1), (1, 1)],  # (вперёд, вправо) от робота
              satellite=False,      # True — режим «со спутником»: поза и карта целиком
              capacity=1,           # сколько труб везёт робот
              step_delay_ms=150)    # пауза после команды, чтобы видеть движение

@sim.on_iteration                   # кнопка «Новая итерация (скан + проезд)» в окне
def step(sim):
    obs = sim.scan()                # obs.scan — список Cell, obs.front — клетка перед роботом
    sim.telemetry(front=obs.front.kind, carrying=obs.carrying)   # таблица в окне
    try:
        sim.forward()
    except IllegalCommand as e:     # e.code: blocked, no_passage, out_of_field, ...
        sim.log(f"нельзя: {e.message}")
        sim.right()

sim.run()
```

Команды: `forward`, `backward`, `left`, `right`, `pick` (труба прямо перед роботом, подъезд поперёк
и с того же яруса), `place(color=None)` (зелёная подставка перед роботом). Нелегальная команда
возвращает HTTP 400 и в Python бросает `IllegalCommand`. Состояние поля при этом не меняется.

Клетка датчика (`Cell`): `kind` — out/floor/section/ramp/tube/stand/holder, `level` — ярус,
`color` — цвет трубы, `ramp_up` — куда поднимается пандус относительно робота,
`tube_axis` — across, если к трубе можно подъехать с текущим курсом. Сырой `id` и абсолютная
поза приходят только в режиме спутника. В режиме хардкор у робота есть только бортовые датчики.

В окне видно: баллы по п.8.3, секции после первого касания трубы и эталон, телеметрию клиента,
журнал, последнюю ошибку. Можно показать эталонный маршрут. Робота можно водить стрелками
(<kbd>P</kbd> — взять, <kbd>O</kbd> — положить).

`python python/examples/follow_reference.py` проходит эталонный маршрут через API и
проверяет всю цепочку: должно получиться 55 баллов и ровно эталонное число секций.

HTTP API: `POST /api/cmd {"cmd": ...}`, `GET /api/scan`, `POST /api/config`, `POST /api/reset
{"index"?, "same"?}`, `POST /api/telemetry {"data", "log", "clear"}`, `GET /api/events?timeout=`
(long-poll кнопки), `GET /api/map` и `GET /api/debug/reference` (только со спутником),
`GET /api/state` (полное состояние для окна).

### Камера робота и освещение

Сервер рендерит кадр трассировкой лучей (`simulator/render.go`), без внешних зависимостей.
Геометрия взята из п.15: баннер 2440 мм, сетка 280 мм, линии 20 мм, секции и пандусы 300×300×100,
круги Ø80, трубы Ø50×250, красная граница. Свет — точечные источники с тенями и бликами
(на чёрной плёнке они как на настоящем поле). Кадр 320×240 со сглаживанием 2×2 рисуется
~30 мс на 4 ядрах.

```python
sim.configure(
    camera={"x": 80, "y": 0, "z": 200,   # мм от центра клетки: вперёд, вправо, вверх
            "pitch": -30,                # к плоскости поля, <0 — вниз
            "yaw": 0, "roll": 0,         # yaw + — вправо
            "fov": 70, "width": 320, "height": 240,
            "aa": 2, "noise": 0.0, "k1": 0.0},   # сглаживание, шум, дисторсия
    lighting={"ambient": 0.35, "shadows": True, "specular": 1,
              "lights": [{"x": 980, "y": 980, "z": 2500, "intensity": 0.75}]},
    scene={"stand_height": 60, "holder_height": 60},
)
png = sim.camera()                    # PNG-байты
frame = sim.camera_array()            # numpy H×W×3 RGB (нужен numpy)
sim.save_camera("frame.png")
sim.camera("satellite", size=640)     # вид «спутника»: 2,8 м над центром, обзор 95° (только satellite=True)
```

Координаты источников света (мм): x — на восток, y — на юг, z — вверх, (0,0) — центр
северо-западного перекрёстка, перекрёсток (col,row) = (280·col, 280·row), центр поля — (980, 980).
Частичные настройки сливаются с текущими, список `lights` заменяется целиком.
На пандусе камера наклоняется вместе с роботом. Корпус робота не рисуется.

Допущения рендера (настраиваются или правятся константами в `render.go`):
- поле симметрично вокруг сетки 8×8 (отступ 240 мм), граница — красная полоса 80 мм вокруг баннера;
- высоты белых и зелёных подставок в регламенте не указаны: по умолчанию 60 мм до низа трубы,
  меняются через `scene`;
- секции рисуются 300 мм, соседние перекрываются на 20 мм (шаг сетки 280).
